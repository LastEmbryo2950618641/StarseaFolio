# 章节入库阶段

## 子阶段：settings-extraction

# settings_extraction

在**草稿已生成、进入图治理之前**，从本轮草稿中抽取应沉淀到 **设定集** 的世界材料。顺序是：草稿 → 设定抽取 → 图治理 → 正文落盘。

宿主在本阶段结束后、图治理开始前，把有效提案写入或更新到 `设定集/`，并把本阶段完整结果追加进图治理上下文。图治理必须同时看见草稿和这些设定。

## 职责

- 识别正文中首次出现或发生实质变化、且适合写入 `设定集/` 的人物、地点、势力、规则、术语与关系；
- 非人物变更输出 **完整 Markdown 草稿** 与目标路径；人物输出 JSON 字段操作；**不得**直接写入工作区；
- 区分「本轮新设定」与「对已有设定文件的更新/合并」。

## 硬规则

- **所有**新增、修改、合并设定集的操作 **只能** 以 `proposals[]` 形式输出；不要声称自己已经写盘。宿主会在图治理前落盘，不再停下来等单独确认；
- 本阶段默认已挂载 `settings-revision`（《设定集修订规则》）全文；按其「正式推演」分支的文件组织与文档结构执行。其中「创作台梗概讨论」与用户确认门禁只适用于讨论侧，本阶段按本提示直接输出提案。非人物路径必须在 `设定集/` 下且以 `.md` 结尾；人物必须为 `设定集/人物/姓名.json`；
- 势力从属、制度层级、组织编制、权力链条等若用文字不便展示，可在 Markdown 提案中直接用 `mermaid` 代码块绘图；
- 遵守本轮阶段附录中的 **「推演发散程度」**：`strict` 禁止 `create`；`world_consistent`（默认）与 `free` 允许相容的新设定 `create`；
- 不得修改 `设定集/readme.md` 的全文替换；若需更新索引，在 `create` 提案中使用 `readmeEntry` 单行索引说明，由宿主在落盘时追加；
- 不得修改 `世界推演规则/`、`参考文件/`、`章节正文/` 或平台基础规则；
- 与已读设定、图、用户规则冲突时，写入 `conflictNotes` 并仍输出提案；宿主仍会在图治理前落盘；
- 若本轮正文没有需要沉淀的设定，返回 **空** `proposals` 数组，并在 `summary` 中说明；
- 不要把章节正文全文复制进提案；只提取设定材料；
- **人物提案**：每人一份 `设定集/人物/姓名.json`，create/update 仅提交 `characterOperations` 字段操作（set/delete），不提交 markdown 或完整 JSON。首次至少完善姓名、性别、性格、背景（对照 `## 性格`、`## 背景`）；未知事实留空，合理补充须说明依据，不得把无个体戏份的集体群像逐一建档。读取与更新既有人物须保留其他字段，禁止 merge 人物 JSON。
- 查询与对照既有设定时遵循《设定集默认查询规则》。
- 作品风格修订不在本阶段；宿主会在下一阶段 `work_style_revision` 单独抽取与融合。

## 提案类型

- `create`：`relativePath` + 完整 `markdown`；可选 `readmeEntry`（一行索引，如「`设定集/人物/林照.json` · 关键词 · 适用章节」）；
- `update`：覆盖写入已有文件的完整新 `markdown`（先基于已读版本修订，不是 diff）；
- `merge`：将多个来源合并进 `targetPath` 的完整 `markdown`，并列出 `mergedFromPaths`。

输出 JSON：`summary`、`proposals[]`（每项含 `payload`、`reason`、`conflictNotes`）、`finalSelfReview`。

人物 payload 示例：`{"kind":"create","relativePath":"设定集/人物/林照.json","characterOperations":[{"op":"set","field":"姓名","value":"林照"},{"op":"set","field":"身份","value":"见习药师"}]}`。人物格式由宿主管理，AI 可新增、删除、更改 fields 内字段，不可改 JSON 外层。

## 子阶段：graph-governance

# graph_governance

重新阅读候选原文单元和相关已提交局部图，在当前 pending scope 提出图治理方案。

`artifacts.settings_extraction` 是本章草稿刚刚抽取、并已写入设定集的结果。把它当作当前设定：其中的人物、地点、势力、规则与关系已经生效，必须和草稿一起决定图变更。`proposals` 为空表示本章没有需要沉淀的新设定。`workStyleRevision` 只是已经落到作品风格的呈现约束，不是世界事实，不要据此改图。

先返回通用执行路由 `executionMode`：`no_change` 表示没有需要更新的图事实，此时 `mutations` 必须为空；`local_governance` 表示依据当前可见局部和你选择补读的证据即可完成本次治理；`full_governance` 表示需要完整治理链、跨局部回溯或无法在当前局部内可靠完成。这三个值只是应用层执行路径，不是人物、地点、时间、关系等预先定义的语义类别。由你根据正文、上下文、图出口规则和读取结果自主判断；代码不会替你枚举或解释影响类型。选择局部治理时，仍必须完整返回本阶段所需的 mutation、检索投影、原文结算、时空绑定、前沿和决定记录，不能为了省请求省略事实覆盖。

- 正文实际出现的每项内容都必须得到持久表达并能返回原文。对正文中可被精确复述、追问或再次指代的文字片段，至少保留其原文作为可精确检索入口，并把入口连接到能够恢复主体、场景、时间、地点及后续变化的局部结构；不要只把它留在章节来源投影或本轮上下文中。
- 对具有可精确复述、追问或再次指代特征的内容，精确文字必须进入 `retrievalProjections[].exactKeys` 或等价的本轮图投影精确键；其语义文本还应说明承载主体、发生场景和时空依据。具体使用节点、连接、信息载荷还是组合结构由你根据局部图决定，不新增固定领域类型，也不按预设内容类别穷举。
- 你可以自主定义和重构局部图的组织与查询语义，不需要为节点或连接套用固定出口类型、进入条件、展开方式或停止字段。
- 优先复用和编辑当前身份；对正文中首次出现且不依赖旧对象的事务，直接创建本轮最小局部身份，不因召回不到旧图而返回空变更。
- 将出现规划作为依据而不是数量许可证。你可以依据当前已读局部和正式正文调整复用、创建、编辑、重构或归档方案；偏离早期规划时必须在决定记录与自审中说明原因。
- 任意 content 或 metadata 内若保存 `local:*` 引用，必须复用本 artifact 已声明的同名局部引用；应用层会递归物化，不能把局部句柄当普通正文字符串。
- 每项修改给出依据、原因、自审、来源和检索投影。
- 当前有效变化连接前置修订及生效时空；归档建立可发现出口，不物理删除历史。
- 为每个场景索引建立 `sceneSpacetimeBindings`；正文场景填写直接覆盖的 `sourceUnitIndexes`，后台无正文演化填写空数组。
- 先逐个阅读本轮全部正文原文单元，再按场景实际覆盖关系填写 `sourceUnitIndexes`；这些索引必须使用输入给出的零基索引，所有场景的并集必须完整覆盖每个原文单元且恰好一次。不能因某场景没有新增图修改而遗漏它所覆盖的原文，也不能把索引覆盖留给后续阶段补齐。
- `sceneSpacetimeBindings[].predecessorSceneIndexes` 必须逐项复制 `dependency_audit.sceneContinuity[].predecessorSceneIndexes`，包括第一个场景可能为空的情况；`predecessorRequired` 为真时也不能为了满足要求虚构 `scene 0` 自己指向自己。
- 当前轮第一个场景若必须承接上一轮，使用 `predecessorSceneAnchorRefs` 指向本轮已读证据映射出的既有图身份，并使用 `transitionPathRefs` 表达从上一轮状态进入本场景的实际路径；`predecessorSceneIndexes` 仍保持与依赖审计完全一致。依赖审计中的 `predecessorSceneRefs` 是证据别名，不能原样当作图引用。
- 为每个图修改建立唯一 `mutationSpacetimeSettlement`。它必须包含 `historicalReturnRefs`；`world_effect` 还必须包含 `currentEntryRefs` 和生效场景；需要继承历史修订时使用实际读取证据的 `evidence_*` 或旧项目 `read-*` 引用，不使用 node owner 冒充 revision。
- `mutationIndexes` 是当前 `mutations` 数组的零基索引；全部修改索引必须在所有 `mutationSpacetimeSettlements` 中恰好出现一次，从 `0` 连续到最后一个索引，不能使用一基编号或遗漏最后一项。
- `settlementRecords` 是可选的原文返回投影，不是新的语义事实；若与场景绑定和修改时空结算重复，可以省略，后台会从这些结构机械生成缺失的原文单元入口。若主动返回，只填写实际知道的零基 `sourceUnitIndex`，不要重复或制造新事实。
- `decisionRecords` 记录需要单独说明的修改决定，可以按共同治理理由分组；未单列的修改自动继承本阶段 AI 返回的总理由和总自审，不要求重复穷举全部修改索引。
- 声明本轮完整的 `affectedFrontierRefs`，供语义审查逐项批准后结算。它只包含本轮确实需要独立继续、暂停或归档的局部演化入口，不是 `mutations` 数组、节点或连接的逐项清单；一个前沿可以承载多项修改，没有受影响前沿时返回空数组。
- 双向邻接接近上限时递归抽象并保留下一层细节。
- 本阶段输入中的 `graphCapacity` 是应用层从当前可见图机械计算的容量画像，不是事实类别或固定领域 schema。先阅读其中的上限、预警值和热点节点；若已有局部超限，必须查询该热点的相关局部后自主决定复用、抽象、合并、编辑或归档，直到新的治理结果不再扩大超限。不要因为容量画像缺少某类细节而拒绝本轮推演。
- `graphCapacity` 只告诉你当前图的容量状态，不替你决定出口含义、合并方式或历史组织方式；这些仍由你依据当前图、原文和上下文自主定义，并在修改原因和自审中说明。
- 治理结果必须完整表达候选正文中全部事务的演化过程与当前有效状态，并能在有限预算内准确、选择性地恢复相关当前状态、历史过程和小说原文。
- 局部含义或组织方式变化时，由你同步重构必要的当前入口、检索投影、历史返回路径和归档结构；如何实现由你决定，不能把旧资料变成不可发现内容。
- 返回检索投影的实际精确键与语义文本、逐原文单元结算映射、连续性载荷和决定记录，不能只返回尚未创建的 ID。

## 子阶段：graph-structure-plan

# graph_structure_plan

阅读正式候选正文、本轮已读证据和依赖审计，形成尚未提交的候选图结构。

- `input.artifacts` 中的正文、涌现结果和依赖审计，以及同一上下文链中更早的正式阶段输出，都是本阶段已提供的直接输入；必须先使用它们，不得把这些已提供内容再次当成待检索资料。
- 正文中出现的万事万物都必须获得可持续存在、可再次发现的图表达；不要按固定领域类型筛选或穷举。
- 你自主决定复用、创建、编辑、局部重构或归档哪些节点和连接，以及其中保存什么信息。
- 每项候选修改使用唯一且稳定的 `proposalRef`。创建的图身份仍使用 `local:*`，后续阶段通过 `proposalRef` 引用这项候选修改。
- 当前状态变化应编辑或连接既有身份；只有本轮新出现且没有可复用身份时才创建新身份。
- 编辑既有节点时，`next` 必须是该节点自包含的最新当前投影：读取当前修订，保留仍然有效的稳定身份、描述和查询入口，再写入本轮变化。不要只返回本轮变化量；旧状态由修订链保存，不要复制进当前投影冒充仍然有效。
- 归档必须保留可发现出口，不物理抹除历史和原文返回路径。
- 本阶段只返回候选结构、受影响前沿、归档出口和决定说明，不生成时空结算或检索投影。
- 图的具体含义、出口定义和局部组织方式由你根据上下文与已有图自主演化；代码不会替你判断语义合并。
- `decisionRecords[].proposalRefs` 的并集必须覆盖本阶段返回的每一项候选修改，且不得引用不存在的候选；每项修改都必须能返回 AI 的修改原因与自审说明。
- 正式候选正文包含内容时，`proposals` 不得为空。缺少旧图资料时，应基于正文、本轮上下文和已读资料形成最小一致的新建或局部更新提案；不得因为旧资料未命中而把整轮正文当作无图变化。

## 子阶段：graph-capacity-rewrite

# graph_capacity_rewrite

只处理应用层容量检查指出的热点局部，不重新生成整张候选图。

- 阅读热点节点、必要邻域、当前候选结构和机械度数结果。
- 自主决定复用、抽象、合并、编辑、重连或归档方式，使候选结构回到配置的入度和出度上限内。
- `affectedProposalRefs` 只声明本次允许删除或覆盖的既有候选提案；删除和覆盖不得超出该集合。
- 可以为局部重写创建新的替代提案；新提案使用新的 `proposalRef`，不把尚不存在的新引用填入 `affectedProposalRefs`。
- 应用层会从旧决定记录中移除已删除提案，并用本次 `reason`、`selfReview` 和仍存活的更新/替代提案形成容量重写决定记录。
- 保持非热点候选提案不变，不重新解释无关局部。
- 重构后必须保留当前状态、演化历史、原文返回和下一层细节的可发现路径。
- 容量指标不定义图语义；修改含义与查询组织仍由你自主决定并说明原因。

## 子阶段：graph-spacetime-settlement

# graph_spacetime_settlement

在容量已经通过的稳定候选结构上结算时间、空间、历史与生效关系。

- 为依赖审计中的每个场景建立对应绑定，保持场景索引和前置场景索引一致。
- 自主确定场景的时间、地点、参照系、实际过渡路径和跨参照对应关系，不预设单一世界时钟或空间类型。
- 任何事物都可以在特定世界中承担时间或空间定位，但放入 `timeAnchorRefs` 或 `locationAnchorRefs` 前必须确认其当前图含义或可达局部确实能够恢复对应的时间顺序、时间位置或空间位置；仅仅可读、相关或出现在场景中不构成锚点用途。
- 使用稳定 `proposalRef` 声明每项候选修改在哪些场景生效，以及它是世界变化还是表示结构重构。
- 当前有效入口、前置修订和历史返回路径必须完整；历史不得因当前状态覆盖而消失。
- 使用 `temporalClaimSettlements` 恰好覆盖依赖审计中的全部时间断言。逐项绑定实际场景、参照事件或状态、时间锚点、AI 选择的时间流或跨时间流对应以及历史返回路径，不得遗漏、重复或新增不存在的 `claimRef`。
- 时间关系无法准确换算时使用 `confidence=uncertain` 并说明已知顺序或范围；不得为了填充字段伪造数值。具体时间含义和对应规则仍由 AI 根据当前局部图定义，不由代码预设。
- 新世界或新局部可以依据正文与上下文合理补全，不因没有旧资料而拒绝结算。
- 只返回时空与历史结算，不重写候选结构或检索投影。

## 子阶段：graph-retrieval-design

# graph_retrieval_design

为稳定候选结构和时空结算定义选择性重新发现方式。

- 自主定义相关查询应进入哪些局部出口、如何选择下一层、何时停止，以及结构变化后如何返回旧含义。
- 对正文中出现的内容建立足以从相关主体、场景、时空和后续变化重新发现它的局部路径。
- 为可精确复述或追问的正文保存精确键，并连接到对应候选图身份和不可变 Source 单元。
- 当前状态、历史过程和原始文字必须能够分别按需返回，不能要求一次加载整张图或全部章节。
- 使用 `ownerProposalRef` 引用本轮候选提案，使用 `ownerRef` 引用已读取的永久身份。
- 只返回检索投影和 Source 结算，不修改候选结构或时空结算。
- 每个 Source 单元必须具有非空图返回路径。多个单元可以复用所属场景或共同局部入口，不需要为每段正文创建节点；不能用空 `graphRefs` 静默表示完成。

## 子阶段：graph-governance-review

# graph_governance_review

审核组合后的候选图，但不要重复输出完整图结构。

- 检查正文中出现的事务是否都被表达，当前状态与历史演化是否同时可返回。
- 对每个 `edit_node` 比较已读当前修订与候选 `next`：候选必须是自包含的最新当前投影，仍然有效的稳定身份、描述和查询入口不能因为本轮只更新了局部状态而无理由消失。旧内容已失效时允许不继承，但必须由修改原因或演化依据支持。
- 检查时间和空间连续性、跨参照对应、精确原文返回、选择性发现、容量与图的简洁性。
- `stageProjection.sourceSettlements` 保留每个来源的 `graphRefSetIndex` 与 `reasonIndex`；二者分别对应 `sourceSettlementReferenceSets[index].graphRefs` 与 `sourceSettlementReasonSets[index].reason`。按此映射逐来源审核，不要把共享引用集或共享原因误认为每个来源都自动成立。
- 逐项核对时空锚点的实际用途：允许奇异事物承担锚点，但它必须按当前图含义或局部可达路径真正恢复时间顺序、时间位置或空间位置；仅因节点可读、相关或在场景中出现而充当锚点，应归为 `spacetime` 修订建议。
- 使用 `temporalClaimAssessments` 逐项恰好覆盖依赖审计中的时间断言。结合原文片段、时空结算和实际 Evidence 判断证据是否充分、正文表达是否一致，并用自由文本说明当前叙述语境；不得用固定叙事类型枚举代替理解。
- 时间断言可以返回 `pass`、`uncertain` 或 `conflict`。`responsibility` 只表示问题应由哪个既有阶段修复，不是时间语义分类；`advice` 只向用户说明后续修改方向，不能拒绝正文或图提交。
- 不得因为正文引入了旧资料中不存在的新事务而拒绝；只检查它是否与已知演化和当前状态矛盾。
- 问题必须归属 `structure`、`capacity`、`spacetime` 或 `retrieval`，让执行器只回退对应的小阶段。
- 尚无 `verificationProbeExecutions` 时，必须返回 `outcome=request_read`，由 AI 在 `requestedReads[].verificationProbe` 中定义至少一个通用验证目的、覆盖范围和查询；应用只负责真实执行，不替 AI 发明探针。已有执行记录时，逐项结合其中的 `returnedReadRefs`、`returnedGraphRefs`、`returnedProposalRefs`、`resultDigest` 以及同一请求中的 `readEvidence` 返回 `verificationProbeAssessments`；字段已提供时不得声称“未提供探针执行结果”，也不得虚构额外探针。
- `retrievalGaps` 中的 `system:retrieval-gap` 只表示对应读取或探针本轮没有执行成功；不得为该缺口生成 `verificationProbeAssessment`，更不得给出 `pass`。Token、时间、模型调用或实际读取错误仍由任务恢复协议处理；选择性读取轮次达到上限时，应用会保留缺口并继续后续审核与提交。
- 没有阻断性问题时返回 `pass`。建议不具有拒绝正文提交的权限，结构契约通过后流程继续。

# semantic_review

使用旧图、完整提案、修改原因、证据和基础规则重新审批图治理结果。

- 不继承 graph_governance 的通过结论。
- 检查身份复用、当前状态连续、双向可发现、局部简洁和归档返回路径。
- 按效果而非固定字段审批 AI 自主演化的局部组织：它必须在有限预算内准确、选择性地恢复相关当前状态、历史过程和小说原文，理论可达但需要大范围无关展开不能批准。
- 检查正文中全部事务的演化过程与当前有效状态均有表达，旧状态不会覆盖新结果，重构也没有切断历史和原文返回路径。对可精确复述或再次指代的正文片段，检查图投影是否保存精确文字入口并连接到主体、场景、时空和演化路径；仅存在章节来源投影不算完成图表达。
- 以已读图的历史修订和当前状态作为连续性基准；图、设定集、参考文件均未覆盖的事物，只需验证其本轮推演的时空与因果入口，不得因缺少旧资料拒绝它。正文出现的万事万物都必须有图表达。
- 检查新增结构是否确实服务于正文并保持局部简洁；不以固定数量替代语义判断。声称复用的决定必须引用本轮已读图身份，章节 evidence ID 不是图身份；本轮首次出现的新事物可以由本轮新建局部结构表达。
- 检查 `affectedFrontierRefs` 是否只包含能够独立继续、暂停或归档并可被重新发现的局部演化入口。它不是修改项、节点或连接的逐项清单；一个前沿可以承载多项修改。发现把全部修改引用直接列为前沿时，应退回图治理收敛前沿集合，而不是留给结算阶段猜测或归并。
- 检查提案只使用本轮实际读取资料与同 scope 新内容。
- 批准项、退回项和验证探针判断都是审查建议；可以只列出实际发现的问题，不需要穷举无异议项。需改结构时给出建议，但本轮正文和图仍直接提交。只要时间、地点和既有状态没有矛盾，不因新事物缺少旧资料而拒绝整轮正文。
- 代码只执行你的结构化审批，不替你判断世界语义。
- 对实际发现的问题给出明确索引或引用；未列出的部分表示本轮没有额外审查意见，不要求重复图治理阶段的完整清单。
- 如果输入中还没有 `verificationProbeExecutions`，必须返回 `outcome = request_read`，并在每个 `requestedReads[]` 中填写 `verificationProbe`，由代码真实执行查询。你只定义通用查询、验证目的和覆盖索引，不能声称已经观察到结果。
- 如果输入中已经有 `verificationProbeExecutions`，不得再次请求相同探针；必须逐项返回 `verificationProbeAssessments`，只用 `probeIndex` 引用执行结果，并给出 `verdict` 与 `reason`。purpose、场景索引和修改时空结算索引已经由应用随执行记录冻结，不得在评估中重复生成。
- `returnedReadRefs`、`returnedGraphRefs`、`resultDigest` 和执行状态由代码提供。你不得生成、覆盖或补造这些字段。空结果可以判断为 `fail` 或合理的 `uncertain`，但判断只能形成审查建议，不得阻止正文和图提交。
- `commit_review` 只给建议，不拥有拒绝提交权限。当前阶段的拒绝只表示需要回到图治理重新形成完整结果。
- 若输入含 `deductionGoalBundle`，必须对照锁定的本章 planned 预期评估正文与图提案，并在可选字段 `goalCompliance[]` 中为每个活跃目标给出 `satisfied` / `partial` / `violated` 与简短 `reason`。`violated` 仅作审查建议，不阻止提交。

## 子阶段：dependency-audit

# dependency_audit

独立审计完整草稿和章节标题实际依赖的旧资料及计划外内容。

- 核对每个依赖过去、正在延续或被再次指代的既有对象是否来自本轮实际读取集合；本轮首次创作的新事物不要求旧资料证据，但必须能从本轮正文和图治理结果返回。
- 正文具体陈述过去动作、持续状态或既有结果时，支持它的 Evidence 必须直接覆盖同一主体、动作或状态以及结果；仅仅提到附近地点、相关对象或相似主题不构成充分依据。现有 Evidence 不足时请求选择性读取，仍无命中则保留不确定性，但不拒绝整轮正文。
- 核对时间连续、地点连续、世界约束和行动主体信息边界。
- 为草稿或后台演化中每个需要独立保持时空连续的局部建立从 0 开始连续唯一的 `sceneIndex`；声明 `predecessorSceneIndexes`、已读旧场景引用、`predecessorRequired`、`correspondenceRequired` 及各自原因。
- 场景清单必须覆盖全部实际场景，本轮第一个场景也不能自动免除前置连续性。
- 请求尾部会明确给出本阶段所属工作流和已持久化正文单元数量，必须以该值为准，不能根据正文措辞或旧阶段产物把普通推演误判成后台演化。
- 已存在正文单元时，`sceneContinuity` 不得为空，必须根据完整草稿建立覆盖全部实际场景的清单，供后续图治理把每个正文单元绑定到对应场景；只有没有正文单元的后台演化才可能没有正文场景。
- 由 AI 自主提炼正文中“其真实性依赖某种时间关系成立”的表达，写入 `temporalClaims`；不使用固定时间词表、正则分类器或预设时间关系类型，也不能因为表达方式陌生而跳过。正文中确实没有此类表达时返回空数组。
- 每个时间断言使用唯一稳定的 `claimRef`，定位 `sceneIndex`、正文单元和原文片段，自由说明参照事件或状态、时间流或参照系、关系含义、当前结论、依据及仍缺少的资料。代码只检查引用和覆盖，不替你解释自然语言。
- 时间断言所需证据已经在当前可见链或 `readEvidence` 中时直接使用；只有相关历史已被移出可见上下文且现有 Evidence 无法返回时才请求选择性读取。仍无命中时保留不确定性，不阻断正文。
- 以本轮已读图及修订链核对过去万事万物和当前状态；设定集、参考文件只补充未覆盖的背景。三类资料均未覆盖的新事物按本轮推演审计，不要求为它寻找不存在的旧依据。
- 计划外新内容需要记录审计建议，并可回到出现规划，但不能仅因计划外或缺少旧依据而阻断正文。
- 缺失旧依据时，只有正文确实把该对象当作既有事实继续使用才回到检索；否则将其视为本轮新建或保留不确定性，继续检查时间、地点、当前状态和信息边界。
- 正式正文未闭合前保持 pending。

# frontier_settlement

只结算 `semantic_review` 已批准的 `affectedFrontierRefs`。每个引用恰好出现一次；每个 active/deferred 前沿必须保存最后场景、局部时间、地点、对应结构和重访条件，archived 可以省略重访条件但必须保留历史返回路径。系统处理时间不能写入世界时间引用。

`affectedFrontierRefs` 表示本轮确实需要独立继续、暂停或归档的局部演化入口，不是本轮 `mutations` 的索引，也不是所有被创建、编辑或连接到的节点/连接的清单。一个前沿可以承载多个修改；只有当局部结构本身形成可被后续调度和重新发现的持续演化边界时，才把它列为前沿。没有受影响前沿时返回空数组。

结算时先逐项对应已批准的前沿引用，再为每个引用给出它自己的最后场景、时间和地点锚点。不要为了填满数组复制同一锚点，也不要把修改引用临时提升为前沿引用；前沿的数量和组织方式由当前图与本轮推演决定。

正文场景存在时，最后场景、时间和地点锚点只能复用本轮已经通过时空结算和语义审核的对应锚点。没有正文场景的后台演化可以继承该前沿在本轮已读状态中保存的最后场景、时间和地点锚点，但只能继承同一个前沿自己的锚点。不能因为某个无关节点可读，就在本阶段临时把它解释为时间或地点锚点；若既没有新绑定，也没有该前沿的已读旧锚点，应在审核建议中指出，而不是自行改写用途。

结算本轮受影响局部的自治演化前沿身份。

- 复用已有前沿身份，避免重复创建同一局部入口。
- 对仍可能发展的局部记录推进原因、重访条件和最后推演时间锚点。
- 暂时稳定的局部迁入可发现归档结构，不物理删除。
- 多个局部可能冲突时保留联合演化入口，不分别提交矛盾结果。
- 即使不进入前沿，也记录有依据的判断原因。

# commit_review

汇总本工作流要求的全部阶段证据，给出 `recommendation: commit | revise | retire`。该建议只用于展示连续性风险和后续改进方向，不是拒绝提交的权限，也不能改变阶段 envelope 的继续/批准结果。

- 检查阶段链完整、结构摘要匹配、实际读取依赖闭合且 scope 一致。
- 正式正文必须通过章节命名、依赖审计、图治理、语义复核、原文结算和前沿结算。
- 只有图能够完整表达正文事务的演化与当前有效结果，并能在有限预算内准确恢复相关当前状态、历史过程和原文时才能提交；查询组织方式由 AI 自主演化，不以固定出口字段验收。
- 只读回答不得混入图提交；后台演化不得发布章节文件。
- 检查重点是时间连续性、空间连续性、既有万事万物的演化和当前状态是否矛盾；正文中首次出现且不与已提交世界矛盾的新事物，不因缺少旧资料而被判为失败。
- 将时间断言审核结果汇总到 `continuityAdvice`，保留 `claimRef`、原文定位、结论、实际 Evidence、问题摘要和建议方向。没有问题时也可保留简短 `pass` 结果，便于用户追溯本轮审查依据。
- `continuityAdvice` 只能展示风险和建议，不能阻断提交；即使存在 `uncertain` 或 `conflict`，仍按既有结构门禁直接提交正文与图，由用户决定是否编辑正文。
- 即使建议为 revise 或 retire，只要结构、图修订、原文结算、检索投影和时空连续性门禁已完成，仍然正常提交正文与图；建议和理由必须保留供用户查看。
- 代码负责机械检查和持久化，最终是否修改正文属于用户后续编辑行为，不由本阶段阻断。

# chapter_naming

仅为正式正文生成连续章节标题，并指定所属卷。

## 卷（硬门禁）

- 每个章节**必须**属于某个卷文件夹；**禁止**直接放在 `章节正文/` 根下。
- 卷文件夹命名：`第N卷 标题`（「第N卷」与标题之间有空格）。示例：`第一卷 潮水退去时`。
- **卷序号唯一**：项目中只能有一个「第一卷」、一个「第二卷」等；若该序号卷已存在，必须复用其完整文件夹名，不得另起同序号异名。
- 系统会创建/使用卷目录：`章节正文/{volumeFolderName}/`，并把正文发布为 `章节正文/{volumeFolderName}/{heading}.md`。
- 若卷名不合规（缺「第N卷」、缺标题、含路径分隔符、与已有卷序号冲突等），本阶段会被拒绝并要求你按错误说明重写 `volumeFolderName`。

## 章节标题

- 读取最后一个已提交章节、当前草稿、规则快照及当前时空依据。
- 生成唯一、合法且连续的「第一章 xxxx」形式标题，章节序号和名称都由你决定。
- 输出 `heading`（章节标题）与 `volumeFolderName`（卷文件夹名）；不要生成或维护独立文件名。
- 系统从 `heading` + `volumeFolderName` 机械派生路径，并把正文第一行装配为 `# <heading>`。
- 若本章已有同序号的 `[剧情梗概]` / `[剧情细纲]`，`heading` **必须**与其标题主干一致（含「第N章 …」）；不得另起与规划文件不同的章名。系统会在发布时强制对齐。
- 标题是第一个原文单元，必须参与后续结算。
- 不把 pending、retired 或只读回答当作正式章节历史。
- 同一故事弧线的章节应复用同一 `volumeFolderName`；开新弧线时再新建下一卷（如 `第二卷 …`）。

## 阶段指南：settings-revision

# 设定集修订规则

在 **创作台剧情梗概讨论** 及用户明确要求维护世界材料时，你可能需要 **新增或修订设定集**（`设定集/` 下的 Markdown）。本规则说明如何撰写、组织与提交设定修订；查询既有设定时仍遵循《设定集默认查询规则》。

## 1. 何时修订设定集

### 正式推演（`settings_extraction` 阶段）

章节写入正文的顺序是：**草稿 → 设定抽取 → 图治理 → 正文落盘**。

设定抽取从本章草稿识别应沉淀的材料，并以提案输出。宿主随即把有效提案写入或更新 `设定集/`，并把抽取结果追加到图治理上下文。图治理据此治理世界图，完成后正文才落入章节。这一步不再停下来等单独确认。

- 抽取阶段只输出提案，不直接写文件；
- 若本轮无新设定，返回空提案，图治理直接继续。
- 作品风格不在设定抽取阶段改写；宿主会在下一阶段 `work_style_revision` 按用户原话与本轮正文呈现线索融合 `表现输出/本作品描写/作品风格.md`。

### 创作台梗概讨论

在梗概讨论中，先把可沉淀信息写入工作区 **`暂存区/`**（中间态）。需要写入权威设定时：

1. 产出 `stagingPromote`（完整 Markdown + 目标路径）；
2. 在 `choices` 中给出 `promote_staging`；
3. **等待用户确认落盘**；确认前不得声称已写入 `设定集/`。

在梗概讨论中，若出现以下情况，应**提议**修订设定集（而非只在对话里口头约定）：

- 本章梗概依赖**尚未建档**的人物、地点、势力、规则、术语或关系；
- 需要将讨论中已确认的世界细节**沉淀**为可检索的设定，供正式推演读取；
- 用户规则或梗概要求引用固定设定，但索引中无对应文件或内容不足；
- 用户明确要求补充、修改或拆分设定文件。

以下情况 **不要** 直接改设定集：

- 仅讨论情绪、节奏、选项而未形成可落盘的世界事实；
- 与已提交正文、已读取图当前状态冲突且用户未确认处理方式；
- 属于本轮推演才会首次出现、且更适合在正式推演 **设定抽取** 阶段沉淀的内容（梗概中可标注「待推演建立」）。

## 2. 用户确认（硬门禁）

讨论里通过 `stagingPromote` 写入设定集之前必须：

1. 用一句话说明意图、受益章节/范围；
2. 列出与已提交正文、图、用户规则、已有设定的可能冲突；
3. 给出建议：「仍要更新 / 绕开写梗概 / 放弃」；
4. **等待用户明确同意**（创作台通过「确认落盘」/`promote_staging`）；不得替用户保存，不得在 JSON 回复中假装已写入。

用户同意后，由应用写入 `设定集/`（并更新 readme 索引）；你的职责是给出**完整、可直接落盘的 Markdown 草稿**与目标路径（放在 `stagingPromote.settingsWrites`）。

创作台按钮「确认落盘到设定集与目标」= 批准挂起的 `stagingPromote`（设定写入 + 可选捆绑的 `goalProposals`）。其中「目标」不是要求你先去找 active 目标；没有 active 目标也可以只落设定。

## 3. 文件组织

- 根目录固定入口：`设定集/readme.md`（不可删除）；**每次新增/重命名/拆分文件后，必须同步更新 readme 索引**；
- 一主题一文件优先：如 `设定集/人物/林照.json`、`设定集/地点/盐雾城.md`、`设定集/势力/北境商会.md`；
- 路径使用中文或语义清晰的文件夹分层；文件名应稳定、可检索，避免「新建.md」「临时.md」；
- 单文件过长时按 **身份 / 地点 / 势力 / 规则 / 术语** 拆分，并在 readme 中交叉引用。

## 4. 推荐文档结构

每个设定文件建议包含（可按题材增减）：

```markdown
# {标题}

> 适用范围：{全书 / 第 N 章起 / 某线}; 关键词：{…}

## 身份摘要
（**人物文件必填**。须写明**姓名**与**性别**，并可加一句身份定位；禁止只写绰号或「某人」）

## 性格
（**人物文件必填**。动机、恐惧、处事习惯、说话方式；须与同书其他角色可区分；禁止空泛「冷静/善良/坚韧」堆砌）

## 背景
（**人物文件必填**。出身、关键经历、当前处境与重要关系中的具体锚点；须能解释其为何如此处事）

## 当前约束
（对本作品推演仍有效的规则、状态、禁止项；区分「已发生」与「规划」）

## 细节
（外观、历史、关系、能力、地点特征等）

## 叙事边界
（不可提前揭示、仅特定主体可知、与大纲相关的揭示节奏）

## 关联
（相关设定路径、图入口提示、用户规则引用）
```

写作要求：

- **人物类文件（`设定集/人物/`）硬性要求（最小档案）**：必须具备 **姓名、性别、性格、背景**——`## 身份摘要`（含姓名与性别）、`## 性格`、`## 背景` 不得缺失、不得用「待补」占位；缺任一项的人物提案视为不合格，须补全后再请用户落盘；
- **称谓与正文一致**：档案主键用姓名；梗概/正文指称该人须使用姓名（可辅以称谓，不得匿名替代已建档个体）；无个体戏份的集体群像（如「军队上万人」）不必建人物文件；
- **已发生事实**与**未来规划**分开写；规划不得伪装成过去已提交事实；
- 使用稳定称谓，与正文、梗概、图节点命名保持一致；
- 不写完整章节正文；设定是材料，不是表现输出；
- **架构可直接绘图**：若势力从属、制度层级、组织编制、权力链条、派系关系等用文字罗列不便读，可直接在 Markdown 中用 mermaid 代码块（语言标记为 `mermaid`）绘图，如 flowchart、graph、sequenceDiagram；宿主在设定文档的渲染视图中展示，便于用户一眼看清结构；
- 新增术语在 readme 索引中补一行：路径、关键词、适用条件。

## 5. 修订已有文件

- 先按《设定集默认查询规则》读取现有全文，再提议修改；
- **增量修订**优先：在对应章节下追加或改写，避免无说明的大段删除；
- 若用户手工编辑过设定（与 Agent 上次写入不一致），**必须**视为用户意图，不得悄悄改回，除非用户明确要求；
- 需要推翻旧设定时，在文档中用「修订说明」记录原因，并提示与已提交正文/图的一致性处理。

## 6. 与梗概、推演目标的关系

- 梗概文件（`章节正文/…[剧情梗概].md`）写「本章发生什么」；设定集写「世界是什么、约束是什么」；
- 梗概中可引用设定路径（如「见 `设定集/人物/林照.json`」），但不应把大段设定全文粘贴进梗概；
- 推演目标（goal）描述叙事目的；设定集描述世界材料。二者可互相引用，不要混为同一文件。

## 7. 硬边界

- 不得修改 `世界推演规则/基础规则/` 下任何平台只读文件；
- 不得用设定集修订绕过图治理或提交复核；讨论落盘仍须用户确认，正文发布前的设定抽取由宿主在图治理前写入；
- 不得将参考文件内容原样复制为设定集而不加采用说明；
- 用户规则在明确适用范围内优先；与本规则冲突时，以基础规则与用户明确选择为准。

## 人物资料专用通道

人物是上述 Markdown 规则的例外：新增人物一人一份 `设定集/人物/姓名.json`。先读 `世界推演规则/人物设定.md`；通过 `character_update` 工具增删改字段，禁止用 stagingPromote、markdown、文本替换或 bash 覆盖 JSON。外层结构由宿主管理，fields 内允许按剧情扩展。旧 Markdown 保留供阅读，后续人物资料使用 JSON。
